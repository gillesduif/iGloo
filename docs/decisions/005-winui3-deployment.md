# ADR-005: WinUI 3 Deployment - Unpackaged, Framework-Dependent Dev, Self-Contained Release

**Status:** Superseded by ADR-006 (WPF replaces WinUI 3) 2026-05-18. Kept as audit trail: the WinUI 3 deployment model below no longer applies to the project.
**Date:** 2026-05-17

## Context

WinUI 3 apps can be deployed in two ways:

1. **Packaged (MSIX)** - distributed via a `.msix` installer or the Microsoft Store. The app runs in a sandboxed AppContainer identity, requires package signing for sideloading, and the Windows App SDK runtime is always present (bundled in the package).
2. **Unpackaged** - distributed as plain executables with no MSIX envelope. No sandboxing, no Store requirement, but the app must locate the Windows App SDK runtime itself.

iGloo needs to:
- Run as Administrator (UAC elevation) to query WMI, inspect partitions, and write the boot manager.
- Ship as a simple redistributable without requiring users to have a Microsoft Store account or accept an MSIX install prompt.
- Work offline on air-gapped machines being migrated to Linux.

## Decision

**Unpackaged deployment, framework-dependent during development, self-contained for release distribution.**

## Deployment model details

### Unpackaged

`WindowsPackageType=None` and `EnableMsixTooling=false` in the csproj. No MSIX is generated: the output is a regular Win32 executable directory. This removes the need for package signing, the Store, or App Installer.

### Always self-contained (dev and release)

`WindowsAppSDKSelfContained=true` and `SelfContained=true` are set unconditionally in the csproj. This bundles the Windows App Runtime DLLs alongside the executable for both `dotnet build` and `dotnet publish`. `Bootstrap.Initialize` is never called.

The runtime is loaded via a `[ModuleInitializer]` auto-generated by the WinAppSDK NuGet package (`UndockedRegFreeWinRT-AutoInitializer.cs`), which sets the `MICROSOFT_WINDOWSAPPRUNTIME_BASE_DIRECTORY` environment variable to the app directory before `Main` runs.

This means:
- No machine-installed Windows App Runtime required on any machine (dev or end-user).
- No MSIX visibility problem with elevated processes (the per-user vs. machine-wide Bootstrap issue is eliminated entirely).
- Dev builds and release builds are identical in runtime behaviour - no "works on my machine" surprises.
- `dotnet publish -c Release -r win-x64` produces a self-contained xcopy-deploy directory with no additional flags needed.

## MSBuild `AppxMSBuildToolsPath` workaround

WinUI 3 uses MRT Core (`MrtCore.PriGen.targets`) to compile XAML resources into `.xbf`/`.pri` files. The tasks are in `Microsoft.Build.Packaging.Pri.Tasks.dll` and `Microsoft.Build.AppxPackage.dll`, which live under VS 2022's MSBuild directory:

```
C:\Program Files\Microsoft Visual Studio\2022\<Edition>\MSBuild\Microsoft\VisualStudio\v17.0\AppxPackage\
```

When building via `dotnet build` (not inside VS), `MSBuildExtensionsPath` points to the .NET SDK directory, which does not contain these DLLs. `Directory.Build.props` at the solution root sets `AppxMSBuildToolsPath` by probing the VS 2022 install path for each edition (Enterprise → Professional → Community → BuildTools).

Key lessons learned:
- `$(VisualStudioVersion)` is **not** available in `Directory.Build.props` - it is injected by VS after MSBuild loads. Hardcode `v17.0` for VS 2022.
- `$(MSBuildProgramFiles32)` resolves to `C:\Program Files (x86)` even on 64-bit machines. VS 2022 is 64-bit and installs under `C:\Program Files`. Use `$(ProgramFiles)` instead.

## NuGet version pinning

`Microsoft.WindowsAppSDK` version `1.5.240428000` (WinAppSDK 1.5.3, MSIX `5001.373.1736.0`). Earlier experimental builds (e.g. `1.5.240311000`) reference MSIX sub-packages that are not present in the stable runtime installer and cause Bootstrap to fail even when a stable runtime is installed.

## Platform constraint

WinUI 3 and `WindowsAppSDKSelfContained` require a concrete platform (`x64` or `ARM64`). The `dotnet` CLI defaults to `AnyCPU`. The csproj overrides this:

```xml
<Platform Condition="'$(Platform)'=='' OR '$(Platform)'=='AnyCPU'">x64</Platform>
```

`EnableDefaultApplicationDefinition=false` prevents WinUI from auto-generating a `Main` method in `App.g.i.cs` that would conflict with the custom `Program.cs` entry point.

## Consequences

- No MSIX signing or Store submission required for release.
- No runtime prerequisite on any machine - dev or end-user.
- The `Directory.Build.props` workaround is VS-version-specific: if the project ever moves to a CI agent without VS 2022, it would need a Build Tools installation.
