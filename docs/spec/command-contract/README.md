# iGloo command contract V1

This is an open, versioned interoperability specification for local iGloo capabilities. It is not an industry standard. The words MUST, MUST NOT, SHOULD and MAY have the meanings in RFC 2119 and RFC 8174 when written in capitals. The CLI is the executable public gateway; the execution engine is the logical Core (Core, Preflight, Iso, Migration, UsbWriter, recovery and distro providers). The CLI MUST NOT implement a second installer. Machine clients MUST use the structured CLI interface and MUST NOT parse human terminal output. The current Community Host binding and Fleet fixture Host binding remain transitional for capabilities whose CLI parity is not yet established.

## Status and scope

The current runtime implements `system.version`, `system.capabilities`, `system.capability.describe`, `system.inspect`, `system.inspect.detail`, `distro.list`, `distro.inspect`, `distro.compatibility`, `migration.inspect`, `migration.plan`, `migration.plan.read`, `migration.target.bind`, `migration.target.allocate`, `recovery.inspect`, `operation.status`, `migration.status`, `iso.acquire`, `artifact.acquire` and `artifact.status`. `migration.plan`, `migration.target.bind` and `migration.target.allocate` are PLAN capabilities; `iso.acquire` and `artifact.acquire` are low-risk cache MUTATION capabilities; the others are QUERY capabilities. `migration.plan` is explicitly `AdvisoryOnly` and `executable: false`. `recovery.inspect` currently reports `ObservationUnavailable` and no exact snapshot; it does not claim recovery readiness. `migration.status` can read a future local migration journal entry but no public migration mutation creates one yet. Both ISO acquisition capabilities invoke the existing cryptographic service and omit the private cache path. `Igloo.Core.Host` composes the local backend used by CLI and by transitional Community/Fleet paths. One's unfinished shell and Fleet's development assessment path now use `Igloo.Cli.Client`, which launches the CLI executable. Community's private staging sequence still handles sensitive input and `MigrationManifest` locally, with no public command that accepts it. Fleet's network work types remain assessment and dry run only. No migration, installation, recovery mutation or remote destructive execution capability is registered. An unregistered capability MUST return `UnsupportedCapability`.

`system.inspect.detail` is a separate V1 query so the established `system.inspect` result remains unchanged for strict clients. It returns the V1 summary plus disk/partition geometry, observed free and shrinkable bytes, and counts of Linux installations and installer leftovers. Disk ordinals are display order only; they are neither stable physical identities nor valid mutation targets. Raw device IDs, partition labels, disk models, GPU strings, finding messages and remediation text are omitted. Unknown finding codes become `ProviderFinding` with their severity preserved. CLI users can call `Igloo.Cli.exe inspect detail --json`.

The local capacity evaluator now distinguishes known available, measured insufficient, unknown, physically too small and ambiguous boot-disk observations. `migration.inspect`, `migration.plan` and Fleet's transitional trusted dry-run adapter use this same calculation, then map it into their distinct transport records. The catalogue Secure Boot rule is evaluated alongside provider compatibility in Runtime for CLI and Host callers; Community no longer duplicates that rule. These observations remain advisory and do not bind an installation target.

`artifact.acquire` calls the same ISO acquisition coordinator, cross-process lease and operation journal as `iso.acquire`. After the service verifies the downloaded bytes, Core records an `ArtifactId` derived from provider ID and the verified SHA-256, together with private cache provenance under the user's local iGloo artifact directory. The public result contains ID, digest, size and GPG verification state, never the cache path. `artifact.status` reopens that registry and hashes the current cache bytes; it reports `verifiedNow: false` for missing or changed content. A malformed or corrupted registry record returns `VerificationFailed`. `ArtifactId` is content identity, not a durable target binding or authorization to install. No public migration command consumes it yet. The registry's local path is private storage, separate from the operation journal and `MigrationManifest`; access control and cross-reboot installation use require further review.

`migration.plan` has capability versions 1 and 2. V1 keeps its original strict result shape for existing machine clients. V2 returns a random `PlanId`, typed `capacityState`, the advisory findings, a provider revision fingerprint, an `observedMachineFingerprint` for the read-only observation, and an `observedStateFingerprint` bound to the observed machine revision, provider binary, loaded catalogue and distro ID. Core saves only this non-secret plan metadata under `%LOCALAPPDATA%\Igloo\plans` with schema version and an integrity digest. `migration.plan.read` retrieves it by PlanId after a CLI/client process restart. `Igloo.Cli.exe migration plan <distro> [requested-bytes]` chooses V2; `Igloo.Cli.exe migration plans read <plan-id>` reads it. Explicit V1 machine requests remain supported. Discovery describes the highest available capability version. Neither V1 nor V2 plan is executable; a saved PlanId is not approval, exact target identity, or an operation ID. The integrity digest detects accidental corruption, not hostile tampering by the local account. No prepare/execute handler consumes a plan yet.

`migration.target.bind` V1 accepts `{ "planId": "<UUID>" }` and returns `{ "planId": "<UUID>", "targetId": "<UUID>", "boundStateFingerprint": "<SHA-256>", "executable": false }`. It reloads an unblocked V2 advisory plan, rechecks the provider and preflight revisions, and observes the Windows boot volume twice using Core's canonical storage identity: provider unique disk identity, GPT disk and partition GUIDs, volume GUID, disk and partition geometry, sector sizes and filesystem. The observed disk number only correlates the same inventory with preflight; it is never stored as authority. A random opaque TargetId maps to a private record under `%LOCALAPPDATA%\Igloo\targets` containing the PlanId, plan revision and canonical identity hash, not raw serials or paths. Reopening this record requires the same plan and a fresh matching canonical identity; a replaced disk or changed geometry fails closed. The record's SHA-256 digest detects accidental corruption, not hostile modification by the local account. This TargetId binds the current Windows boot disk identity, not an exact future free-space extent or installer allocation. A TargetId is **not** approval, a prepared operation or permission to mutate. If exact identity cannot be observed, binding returns `PreconditionFailed`; stale plan or target facts return `StateChanged`.

The broader target remains incomplete. Community now calls Host interfaces for its preflight, ISO, staging, installation-preparation, USB and Windows-maintenance paths; those private in-process interfaces preserve the existing services and UI behavior. They are not public command capabilities. Fleet Agent's trusted assessment and dry run use the typed CLI client; its Host adapter remains for fixtures and transition tests. The trusted Agent passes its configured provider directory to the child CLI through a process-scoped `IGLOO_DISTROS_DIRECTORY` setting. Fleet rejects dry-run evidence when inspection, plan and compatibility observations disagree. A file operation journal records ISO acquisition, and advisory migration queries return a revision fingerprint. The new advisory TargetId is a canonical physical identity binding, but it is not a cross-reboot install implementation or execution authority. No endpoint-destructive command may be registered until exact identity, approval, stale-state checks, recovery gates, replay protection and continuation are integrated and tested. `MigrationManifest` remains private local execution/handoff state, never a public command result or Fleet transport record.

The [implementation report](implementation-report.md) records the exact baseline, current project graph, validation results and remaining blockers.

## Advisory allocation intent

`migration.target.allocate` V1 accepts `{ "planId": "<UUID>", "targetId": "<UUID>", "requestedShrinkBytes": 64424509440 }`. It returns a fresh `allocationId`, `observedLayoutRevision`, the exact proposed NTFS shrink amount and resulting partition size/free offset, `capacityState: "KnownAvailable"`, `warningCodes: ["InstallerLayoutNotBound"]`, `scope: "WindowsBootNtfsShrinkIntentV1"` and `executable: false`. This is one precise **proposed Windows boot-partition shrink**, not the complete installer partition allocation. The request must cover at least the plan's required Linux bytes; the caller's requested amount does not certify installer overhead. The provider's stage-2/seed/ISO sizes and the current DirectInstallService selection/reuse behavior are not bound. Therefore this AllocationId MUST NOT satisfy a future `migration.prepare` until a reviewed capability version binds the whole installer mutation and the executor consumes the same geometry.

Core reloads the advisory PlanId and TargetId, checks their current revisions, identifies the NTFS source by canonical GPT/volume identity, reads the complete disk partition geometry and the Windows storage provider's exact supported-size minimum/maximum, and observes the layout twice. The saved opaque ID under `%LOCALAPPDATA%\Igloo\allocations` contains only plan/target IDs, requested/resulting sizes and a hash of the canonical layout and size limits. It contains no raw disk identity, credential, manifest or private path. Reopening requires fresh matching target and layout observations; partition replacement, geometry/size-limit change, disk replacement or corrupt metadata fails closed. Disk enumeration order is absent from the layout revision. The record integrity digest detects accidental corruption, not hostile local-account edits. No disk operation occurs while issuing or reopening an AllocationId.

PlanId expresses intent; TargetId binds the physical Windows boot disk; AllocationId V1 binds only this shrink intent; ArtifactId identifies verified installer bytes. None grants approval or execution. `recovery.inspect` remains unavailable for exact readiness; no RecoveryId, SecretHandle, approval reference or migration OperationId is issued. The [implementation report](implementation-report.md) records the secret lifetime audit, recovery gaps, ownership and continuation design.

`LayoutId` is reserved for a future, separately versioned finalized installer-visible storage transformation. No LayoutId exists today. The current private direct-install service is guarded before mutation by unsupported dedicated-ESP preparation; its legacy code would otherwise select the Windows shrink source and free extents dynamically. Fedora's current installer recipe also selects a disk by size with a largest-disk fallback and uses dynamic autopart. Neither path consumes AllocationId V1 or an exact finalized layout. No public command may promote the advisory AllocationId to a complete layout without removing those mismatches and proving installer/provider parity.

An internal reviewed-preparation binding now extends the existing `PreparationPlanV1` with the proposed exact Windows shrink, pre-layout, freed extent, artifact/media facts and provider revision. Fixture code can issue a shrink receipt only after a matching provider result and independent readback, and Fedora has an opt-in renderer for owned installer partitions that refuses saved Wi-Fi. The production Windows exact writer, artifact/provider revalidation, recovery proof and cross-reboot handoff are still missing; the dedicated-ESP gate remains closed. This internal work does **not** create a LayoutId or register `migration.prepare`, `migration.execute` or `migration.verify`. The [implementation report](implementation-report.md#reviewed-installer-layout-substrate-2026-10-07) distinguishes the fixture-tested contracts from production execution.

The existing browser credential envelope uses a password-derived key that the user enters again after installation. It does not provide an unattended cross-OS key for Wi-Fi. Current private staging writes Wi-Fi PSKs in plaintext into the internal manifest and Fedora installer config; the public command contract MUST NOT accept that handoff as safe secret custody. No public SecretHandle, RecoveryId, LayoutId, execution approval or migration OperationId is issued. The [current investigation](implementation-report.md#finalized-layout-and-custody-investigation-2026-10-07) records the exact safety blockers and the internal, non-authorizing execution-intent fingerprint.

## Request and result

JSON uses camel-case property names and string enum names. `protocolVersion` and `capabilityVersion` are integers; `requestId` and `correlationId` are nonempty UUIDs. `input` MUST be an object matching the capability schema. `dryRun` is rejected unless discovery says the capability supports it. An `operationId` identifies accepted long-running work where implemented; ISO acquisition now persists safe lifecycle metadata in a local file journal. `idempotencyKey` remains reserved. `observedStateFingerprint` identifies an observation revision for advisory migration results; it is not authorization or a durable target identity. Its presence cannot enable mutation. The current `iso.acquire` is resumable through the existing cache and serialized per distro with a cross-process lease.

The response repeats protocol, capability and correlation fields. `succeeded` is authoritative. On success, `data` is typed by `resultSchemaId`; on failure, `error.code` is stable and no uncontrolled exception text is emitted. `warnings` and `evidence` are arrays, even when empty. Public evidence MUST be allowlisted and MUST NOT contain credentials, private file paths or raw preflight finding messages. The current `system.inspect` returns typed machine facts and finding codes/severities, not raw device IDs or finding text.

The generic envelope schemas are [request.schema.json](request.schema.json) and [result.schema.json](result.schema.json). [capability.schema.json](capability.schema.json) defines discovery metadata. The capability-specific V1 schemas and samples are in [capabilities.schema.json](capabilities.schema.json). The C# records in `Igloo.Command.Contracts` are the executable serialization model. Schema files describe this implemented subset; adding a future capability requires its own reviewed input/result schema and conformance tests.

Example request:

```json
{"protocolVersion":1,"capabilityId":"distro.inspect","capabilityVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","input":{"distroId":"debian"}}
```

Example result shape (the display name is provider catalogue data):

```json
{"protocolVersion":1,"capabilityId":"distro.inspect","capabilityVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","succeeded":true,"data":{"id":"debian","displayName":"Debian","status":"available"},"warnings":[],"evidence":[]}
```

An advisory V1 plan request and result shape (still supported):

```json
{"protocolVersion":1,"capabilityId":"migration.plan","capabilityVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","input":{"distroId":"debian","requestedLinuxBytes":42949672960}}
```

```json
{"protocolVersion":1,"capabilityId":"migration.plan","capabilityVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","succeeded":true,"data":{"distroId":"debian","requiredBytes":42949672960,"blockerCodes":[],"executable":false,"disposition":"AdvisoryOnly"},"warnings":[],"evidence":[],"observedStateFingerprint":"A_FULL_SHA256_HEX_DIGEST_FROM_THE_OBSERVATION"}
```

The placeholder fingerprint above is illustrative; real results contain 64 hexadecimal characters. `observedAvailableBytes` is absent when capacity could not be established. A plan with no reported blocker still cannot be executed. `migration.status` and `operation.status` take `{ "operationId": "<UUID>" }`; unknown IDs return `NotSupported`. Current ISO acquisition creates durable operation records. No public migration operation does.

A V2 request uses the same typed input with `"capabilityVersion":2`. Its result data adds `planId`, `capacityState`, `observedMachineFingerprint`, `observedStateFingerprint`, and `providerRevisionFingerprint`; `executable` remains `false` and `disposition` remains `AdvisoryOnly`. The returned `observedStateFingerprint` is repeated in the standard result envelope. A `migration.plan.read` request uses `{ "planId": "<UUID>" }` and returns the saved V2 plan data. Missing IDs return `NotSupported`; corrupted records return `VerificationFailed`.

## Discovery, versioning and errors

`Igloo.Cli.exe capabilities list --json` returns descriptors. `Igloo.Cli.exe capabilities describe iso.acquire --json` returns one descriptor. Each gives ID, capability version, input and result schema versions/IDs, query/plan/mutation kind, risk, dry-run support, authority requirement, observed-state requirement and applicable provider IDs. Empty provider IDs mean no provider constraint. Consumers MUST check discovery rather than assume every installation step exists.

The CLI supports `version`, `inspect`, `capabilities list|describe`, `distros list|inspect|compatibility`, `migration inspect|plan|status`, `recovery inspect`, `operations status`, `iso acquire`, and `invoke` for a complete JSON request. `migration plan <distro> [requested-bytes]` and `migration target bind <plan-id>` and `migration target allocate <plan-id> <target-id> <shrink-bytes>` are advisory. `--json` yields one result object on stdout; long-running progress stays on stderr in human mode.

The detail, artifact and target-binding additions are `inspect detail`, `artifacts acquire <distro>`, `artifacts status <artifact-id>` and `migration target bind <plan-id>`. Machine clients invoke their capability IDs through the same `invoke --machine` stream.

The command protocol, capability semantics, serialized input/result schemas and product/runtime assembly version are distinct. Protocol V1 rejects other protocol versions. An unsupported capability version returns `UnsupportedVersion`. Compatible additive fields may be introduced only when old clients can ignore them safely. A destructive capability's meaning MUST NOT broaden in a compatible revision; use a new capability version with explicit approval and state binding. Unknown required fields or changed mutation semantics require a new schema/capability version. Deprecation requires a documented replacement and an overlap period; no deprecation is scheduled for this initial subset.

Error codes are `InvalidRequest`, `UnsupportedCapability`, `UnsupportedVersion`, `PreconditionFailed`, `StateChanged`, `ApprovalRequired`, `PolicyDenied`, `ResourceBusy`, `NotSupported`, `VerificationFailed`, `RecoveryRequired`, `Cancelled` and `InternalFailure`. Only the codes exercised by registered capabilities are currently emitted. Future handlers MUST normalize expected failures to this taxonomy without exposing exception class names or uncontrolled messages. CLI exit codes are 0 success, 2 invalid/unsupported command or version, 3 known operational failure, 4 internal failure, 130 cancellation. `invoke --machine` writes a JSON Lines event stream to stdout; human `--json` and legacy `invoke` write one result JSON object. Machine progress is structured on stdout; stderr is diagnostic only.

## Executable machine transport (current implementation)

The CLI project builds `Igloo.Cli.exe`. `iGloo.exe` is the separate Community WPF application and MUST NOT be treated as the CLI. After `Igloo.Cli.exe invoke --machine` starts, it emits an uncorrelated `hello` with CLI product/version and protocol version **before receiving a request**. A first-party client MUST validate that hello before sending one V1 `CommandRequest` JSON line on stdin. The CLI then emits `accepted`, zero or more `progress` frames, then exactly one `result` containing the normal `CommandResult`. Post-hello frames carry the request and correlation IDs. The CLI and the client validate those IDs; the result also repeats the capability and version. [stream-event.schema.json](stream-event.schema.json) describes the stdout frame. This framing is separate from the existing human `--json` option, which still emits one result object.

```json
{"type":"hello","protocolVersion":1,"requestId":"00000000-0000-0000-0000-000000000000","correlationId":"00000000-0000-0000-0000-000000000000","product":"Igloo.Cli","productVersion":"1.0.0.0"}
{"type":"accepted","protocolVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222"}
{"type":"progress","protocolVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","progress":{"requestId":"11111111-1111-1111-1111-111111111111","phase":"validating"}}
{"type":"result","protocolVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","result":{"protocolVersion":1,"capabilityId":"system.version","capabilityVersion":1,"requestId":"11111111-1111-1111-1111-111111111111","correlationId":"22222222-2222-2222-2222-222222222222","succeeded":true,"data":{"protocolVersion":1,"runtimeVersion":"1.0.0.0"},"warnings":[],"evidence":[]}}
```

The version numbers above are illustrative product/runtime values; they are not the protocol version. The hello uses empty UUIDs because the request has not been sent yet. A client MUST treat non-JSON stdout, missing/out-of-order frames, mismatched IDs, incompatible protocol versions and absent terminal results as transport failures. It MUST use `CommandResult.succeeded` and `error.code` for semantic outcomes. The CLI never places request data or secrets in argv: only `invoke --machine` appears there. Stderr is not part of the machine contract and MUST NOT be parsed for success; startup failures may yield only a transport failure. A malformed first request line yields a sanitized `InvalidRequest` result after hello, without a correlated `accepted` frame.

For cancellation, a client may write a second stdin line `{"type":"cancel","requestId":"<same UUID>"}`. The CLI routes this to the dispatcher token and emits a structured `Cancelled` result when the handler cooperates. The process client waits briefly for that result before terminating an unresponsive process. A timeout, unexpected process death or forced termination is a transport failure with **unknown operation outcome**; it is not proof of safe cancellation. Where a durable operation ID exists, a caller can start a new CLI process and use `operation.status` to reconnect. The current journal covers ISO acquisition, not an installation across reboot.

`Igloo.Cli.Client` resolves only the known packaged `cli/Igloo.Cli.exe`/adjacent location or a repository build for development; it does not search `PATH`. It verifies the executable name and Windows product metadata and then checks the protocol `hello`. Metadata and placement are not a cryptographic signature check. Product packaging of the CLI alongside Community, One and Fleet Agent still requires validation; the source-tree fallback is development-only. CLI process startup is measured by tests only for correctness, not yet benchmarked for high-frequency polling. Do not add a daemon without measured need.

Read-only commands use normal user authority. Discovery declares elevated or explicit approval requirements per capability; it does not grant them. No generic shell command is exposed. Private paths, credentials and the local `MigrationManifest` MUST stay out of public results, journal records, argv and Fleet transport. The stdin pipe is the current transient request transport, with a future protected broker possible without changing capability semantics.

## Client-neutral semantics and blocked migration stages

For the same capability version, typed input, observed endpoint state and authority context, an implementation MUST give equivalent semantic results to Community, One, Fleet Agent, human CLI users, scripts and third-party clients. Product identity MAY affect authentication, authorization, audit attribution or policy scope; it MUST NOT change what a capability means. CLI flags govern transport and interaction. Endpoint-domain inputs belong in typed request data. Core/CLI own endpoint capabilities; Community owns graphical workflow; One owns reasoning and tool selection; Fleet owns cohorts, policy, approval workflows and scheduling across endpoints.

`migration.prepare`, `migration.execute` and `migration.verify` are **unregistered**. A PlanId, ArtifactId or TargetId never grants execution. `migration.prepare` cannot yet claim a prepared operation: a protected cross-process SecretHandle with defined lifetime and one-shot consumption is absent; the exact recovery snapshot is unavailable; artifact, capacity and target binding have not been joined into an atomic preparation gate. Passwords and private migration values MUST NOT enter argv, normal public results, Fleet transport or the operation journal. Future custody must define its local authorized consumer, expiration, deletion, crash cleanup and reboot behavior before accepting secrets. A short-lived protected handle is the intended shape, not an implemented capability.

The existing file journal survives process restart for ISO acquisition and permits `operation.status`; it does **not** carry a migration across reboot. Existing cross-process resource leases serialize private Community operations and ISO cache work, but no public migration operation yet owns target, partition-table, boot, staging and recovery leases as one guarded execution. There is no public authority token bound to a prepared operation, no installer/first-boot OperationId continuation, and no postcondition verifier. `migration.status` has no public migration producer. These gates prevent Community's private staging path from moving to CLI today; its user-visible workflow remains on the existing Host boundary. Fleet keeps remote destructive work disabled.
## Authority and operation lifecycle

Discovery declares risk and authority; this is metadata, not a grant. A future endpoint mutation MUST revalidate current target identity, state, approval and recovery readiness at commit time, acquire cross-process resource leases for disk/partition table, boot configuration, staging and recovery state, and retain operation identity/evidence across reboot. Query, plan and mutation are disjoint capability kinds. A plan MUST NOT authorize execution by itself. The local journal stores IDs, state, stage, timestamps and allowlisted evidence codes, not credentials, private paths or manifests. Host wraps current Community mutations in cross-process resource leases, but these private paths still rely on the existing service safety gates; the journal does not yet span Windows, installer and first boot. No durable installation or recovery claim is made.

## Consumers and providers

An independent distro maintainer implements `IDistroPlugin` below Core, supplies a reviewed `distro.json` and signed ISO metadata, installs/registers the provider, and can call `Igloo.Cli.exe capabilities list --json`, `Igloo.Cli.exe distros list --json` and the supported commands without Community. Their own frontend can use the JSON envelope or the machine stream through `Igloo.Cli.Client`. Provider code MUST depend toward Core abstractions and MUST NOT take over disk or boot mutation. A future iGloo One AI layer can inspect discovery and typed results through this same CLI contract; it must not get arbitrary shell execution or direct privileged Core access. Fleet Server remains policy/orchestration only; Fleet Agent is the local endpoint boundary.
