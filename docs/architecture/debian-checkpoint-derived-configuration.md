This is a separately authorized development-lab experiment, not replay, recovery,
rollback, restoration or production preparation. The previous configuration operation
remains OutcomeUnknown and its reservations and aliased working backings are retained.

`ContinueLabSameTarget` is unchanged. `ContinueLabCheckpoint` requires a separate
`OneCheckpointDerivedCoreConfiguration` authorization, the verified successful
predecessor, checkpoint identity, exact source and independently reopened copy
hashes, fresh destination identities and the complete shared inventory validation.
Creation and format receipts remain ancestry; copying does not create new ones.

The trusted exclusive host records the user's one-attempt authorization in a
protected store outside all copied filesystems. It reserves that authorization with
create-new publication before making independent copies. Its producer rejects
preexisting destinations, hardlinks, changed source bytes, incomplete readback and
open retained backings. Source and destination content hashes and inode/device
identities are independently reopened. The final launch attaches only the copies.
Configured serials correlate the controlled launch; they are not Windows identity.

`--configure-derived-lab` is the separate protected harness entrypoint. It verifies
the predecessor chains, checks the protected external authorization against the
derivation envelope, and calls the same shared ownership/lease/session machinery.
The plan includes the validated derivation digest; provider evidence also binds the
authorization and fresh acquisition. New session/effect stores are under
`configuration-derived/<attempt-id>/`, while the external host reservation prevents
a copied clean journal from being interpreted as unlimited retry authority.

A protected declaration is trusted-host input, not release authentication. Guest
JSON alone is not authorization. A compromised exclusive host remains outside this
lab threat model. Production entrypoints do not accept this composition. Neither
same-target nor derived scopes permit import replay, formatting, generic package
execution, initramfs, firmware or target boot.

Before the overall configuration intent, the current executor verifies the neutral
baseline, account before-state, actual view sources and deterministic output parents
and types. The existing broker privately masks `/boot` read-only and binds the
verified empty `/mnt` alias at child `/boot/efi`. It does not create that directory
in the imported root or mount the actual ESP. Each helper still requires its own
durable intent, stopped-gate isolation observations and unchanged-state checks.

The fixed profile and independent delta semantics remain those documented in
[post-import configuration](debian-post-import-configuration.md). Current execution
outcomes and source hashes are recorded separately from the earlier failed attempt.
An unresolved new attempt cannot be automatically relaunched or made resumable by
changing its operation ID. A phase note records evidence and the next permitted
action, not replay authority.
