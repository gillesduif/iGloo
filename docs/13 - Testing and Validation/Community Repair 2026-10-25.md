## Still-open legacy Debian boundaries

**[Source-level, conditional – not observed]** The user's Debian run on 26 Oct with the repaired tree installed and reached first boot (one unexplained VM restart, under investigation), so this condition did not trigger there. Read-only tracing found that the Community legacy staging route calls `RenderInstallerConfigAsync`, which supplies no exact root extent. Its generated partman helper uses the fallback rule: select the sole free region on the identified disk that meets the provider's 20 GiB minimum. The legacy preparation route does not re-render that configuration with an observed post-shrink extent. Consequently, multiple qualifying regions can stop installation after preparation, and a sole prior free region can differ from the requested Linux allocation. These are conditional source-level findings, not observations that every Debian installation fails.

**[Design note, not a defect]** v0.2-alpha never created a dedicated Linux ESP either; the installers use the Windows ESP, which is the shipped and community-tested behaviour. That legacy route also does not create or bind a dedicated Linux ESP, so it does not establish the reviewed Windows-ESP preservation guarantee. The exact-renderer correction above does not repair this separate legacy integration. Reviewed native preparation remains closed pending its storage and boot restoration proofs. Full qualification still requires the actual Debian installation, Linux first boot, imported-data use and return to the retained Windows installation.

## Boot registration failure and repair (r5, 13:12 CET)

**[Verified: application log pasted in chat 25 Oct; source]** After the preparation result above, the operator pressed Restart in the r5 wizard. The application log records, at **13:12:12.035 CET**, `Boot-registration planning blocked: "Unsupported"/BootPlanDeleteReferencesUnavailable`, followed by `CommunityRecoveryBoundaryException: Boot registration was blocked by recovery verification (ScopeUnresolved). No boot changes were started.` from `DirectInstallService.RegisterBootEntry` (line 1589) via `DirectInstallPreparationCompletion.RegisterAsync`, `InstallationPreparation.RegisterBootEntryAsync` and `DirectInstallViewModel.RebootToInstallAsync`. No restart followed. The same path is taken for Mint and Fedora, which explains the earlier observation that every distro failed at the end of the wizard.

Source reading of `CommunityBootRegistrationPlan.Create` locates the refusal: the planner collects every BCD object whose description equals `iGloo distribution installer` as a stale object to delete, and for each one requires `BcdMutationPlanning.InboundReferences` over the whole BCD graph to be `Available`. That function returns `Unsupported` as soon as any element of any object in the store has a value or reference semantics the parser does not model; the WinRE RAM-disk object already identified under issue #242 is one such element. A clean machine has no stale object and passes; every retry after a crash, cancel or earlier alpha run has one and fails. Separately, the planner returns `BootPlanExistingTargetEntryRequiresOwnership` when the firmware already holds an entry for the installer partition, which is the documented Gigabyte/AMI behaviour the v0.2-alpha registration was written to survive.

Repair (source change, uncommitted, isolated in `claude-bootregistration-20261025.patch` at the repository root): `RegisterBootEntry` is the v0.2-alpha logic again, adapted to `CompletedDirectInstallPreparation` (partition geometry from the pinned canonical volume identity rather than a second WMI query). Order: `Boot####` → `\EFI\BOOT\BOOTX64.EFI`, BootNext to the own entry or to the firmware's own entry for the same partition, `bcdedit` stale-entry removal + `/copy {bootmgr}` + `bootsequence`, BootOrder prepend, sibling promotion, `RealTimeIsUniversal=1`. Only the first NVRAM write is fatal. The CommunityRecovery classes and their tests are unchanged and remain reachable through `PlanBootRegistrationForDiagnostics`; they are not on the product path. Decision recorded in [ADR-014](../decisions/014-boot-registration-is-not-gated.md). No build or VM evidence for the repaired source existed when this section was written; the r6 run is the acceptance test (see [[00 - Home/Beta Track]] B-00). **Update 26 Oct:** the user reports that the Debian run with the repaired registration booted the installer, installed and completed first boot (one VM restart was needed to reach Debian; cause under investigation with `/var/log/igloo/first-boot.log`). Mint and Fedora runs are pending.

Also noted from the same log for the beta track: at 13:03:19 staging failed once on `SQLite Error 5: database is locked` for `Edge\User Data\Default\History` (B-03), and each preparation attempt creates a new OEMDRV partition and staging directory (B-01). Edge's App-Bound Encryption message (`passwords cannot be migrated`) is expected behaviour, not a failure.
